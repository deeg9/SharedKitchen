**Helper function** (pattern from is_household_member):
```sql
CREATE OR REPLACE FUNCTION is_kitchen_member(p_kitchen_id UUID, p_user_id UUID)
RETURNS BOOLEAN LANGUAGE sql SECURITY DEFINER STABLE
AS $$
  SELECT EXISTS (
    SELECT 1 FROM kitchen_profiles kp
    JOIN household_members hm ON hm.household_id = kp.household_id
    WHERE kp.id = p_kitchen_id AND hm.user_id = p_user_id
  );
$$;
```

**Trigger for follow counts** (FOLL-03):
```sql
CREATE OR REPLACE FUNCTION update_follow_counts()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE kitchen_profiles SET follower_count = follower_count + 1 WHERE id = NEW.following_kitchen_id;
    UPDATE kitchen_profiles SET following_count = following_count + 1 WHERE id = NEW.follower_kitchen_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE kitchen_profiles SET follower_count = GREATEST(follower_count - 1, 0) WHERE id = OLD.following_kitchen_id;
    UPDATE kitchen_profiles SET following_count = GREATEST(following_count - 1, 0) WHERE id = OLD.follower_kitchen_id;
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_update_follow_counts
  AFTER INSERT OR DELETE ON follows
  FOR EACH ROW EXECUTE FUNCTION update_follow_counts();
```

**RLS Policies** - Enable RLS on ALL tables. Use `(select auth.uid())` subselect wrapper everywhere (not `auth.uid()` directly -- up to 99.99% perf improvement per Supabase docs).

kitchen_profiles RLS:
- SELECT: `is_public = true OR is_kitchen_member(id, (select auth.uid()))` -- anyone can view public profiles, members can view own
- INSERT: `is_household_member(household_id, (select auth.uid()))` -- members can create their kitchen profile
- UPDATE: `is_kitchen_member(id, (select auth.uid()))` -- members can update their kitchen profile
- DELETE: none (kitchen profiles deleted via household CASCADE)

follows RLS:
- SELECT: `true` (all authenticated users can see follow relationships)
- INSERT: `is_kitchen_member(follower_kitchen_id, (select auth.uid()))` -- can only follow AS your own kitchen
- DELETE: `is_kitchen_member(follower_kitchen_id, (select auth.uid()))` -- can only unfollow AS your own kitchen

feed_posts RLS:
- SELECT: `true` (all authenticated users can see feed posts; blocking filtered in app layer)
- INSERT: `is_kitchen_member(kitchen_id, (select auth.uid()))` -- only post as own kitchen
- UPDATE: `is_kitchen_member(kitchen_id, (select auth.uid()))` -- only edit own posts
- DELETE: `is_kitchen_member(kitchen_id, (select auth.uid()))` -- only delete own posts

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated user to social tables | Users can read public data but only write as their own kitchen identity |
| Household boundary to kitchen profile | Kitchen profile is the public face; household internals (grocery, budget, pantry) never exposed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-01 | Information Disclosure | kitchen_profiles RLS | mitigate | SELECT policy only allows viewing public profiles (is_public=true) or own profile via is_kitchen_member(). household_id is in the row but never exposed through social queries -- downstream stores select specific columns, never * |
| T-30-02 | Tampering | follows table | mitigate | INSERT RLS requires is_kitchen_member(follower_kitchen_id). CHECK constraint prevents self-follow. UNIQUE constraint prevents duplicate follows. |
| T-30-03 | Tampering | follower_count manipulation | mitigate | Counts maintained by server-side trigger only. No direct UPDATE policy on follower_count/following_count columns (UPDATE policy exists but trigger handles counts). UNIQUE on follows prevents inflation. |
| T-30-04 | Tampering | kitchen_profiles.bio/display_name | mitigate | Bio CHECK(char_length <= 300). Plain text rendered in React Native Text components (not WebView). UPDATE restricted to kitchen members via RLS. |
| T-30-05 | Spoofing | invite_code brute-force | accept | 8-char alphanumeric = ~2.8 trillion combinations. Rate limiting deferred to Phase 31 follow endpoint. Low risk for invite-to-follow (not invite-to-household). |
| T-30-06 | Information Disclosure | blocked_kitchens | mitigate | SELECT restricted to blocker's own kitchen via is_kitchen_member(blocker_kitchen_id). Blocked user cannot see they are blocked. |
</threat_model>
