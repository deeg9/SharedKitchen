**Step A: Create migration file** `supabase/migrations/00030_public_profiles_view.sql`:

```sql
-- Migration: Create public_profiles VIEW for cross-user profile access
-- Phase 49: Tech Debt & Type Safety (DEBT-01)
--
-- Restricts cross-user profile visibility to safe columns only.
-- Own-profile access continues via direct profiles table with existing RLS.

-- 1. Create restricted VIEW (only safe columns for cross-user access)
CREATE VIEW public_profiles AS
  SELECT id, handle, display_name, avatar_url
  FROM profiles;

-- 2. Grant access to authenticated users
GRANT SELECT ON public_profiles TO authenticated;

-- 3. Drop the overly broad read policy (DEBT-01)
-- Own-profile read (auth.uid() = id from 00001) remains intact.
DROP POLICY IF EXISTS "Authenticated users can read any profile" ON profiles;
```

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-04 | Information Disclosure | profiles RLS broad SELECT | mitigate | Drop "Authenticated users can read any profile" policy, route cross-user access through public_profiles VIEW that only exposes id, handle, display_name, avatar_url (DEBT-01) |
| T-49-05 | Tampering | public_profiles VIEW | accept | VIEW is read-only by nature; INSERT/UPDATE/DELETE on views without INSTEAD OF triggers are rejected by PostgreSQL |
| T-49-06 | Elevation of Privilege | Direct profiles table access after policy drop | mitigate | Own-profile SELECT policy (auth.uid() = id) from migration 00001 remains; cross-user reads are blocked on base table, forced through VIEW |
</threat_model>
