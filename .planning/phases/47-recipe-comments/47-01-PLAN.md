   ```sql
   CREATE POLICY "Users can view recipe comments"
     ON recipe_comments FOR SELECT
     USING (
       EXISTS (
         SELECT 1 FROM recipes r
         WHERE r.id = recipe_comments.recipe_id
         AND (
           is_household_member(r.household_id, auth.uid())
           OR EXISTS (
             SELECT 1 FROM kitchen_profiles kp
             JOIN follows f ON f.following_kitchen_id = kp.id
             JOIN kitchen_profiles my_kp ON my_kp.id = f.follower_kitchen_id
             JOIN household_members hm ON hm.household_id = my_kp.household_id
             WHERE kp.household_id = r.household_id
             AND hm.user_id = auth.uid()
           )
         )
       )
     );
   ```

   ```sql
         SELECT 1 FROM recipes r
         WHERE r.id = recipe_comments.recipe_id
         AND r.created_by = auth.uid()
       )
   ```

**Step 2: Create src/stores/recipeCommentStore.ts** following cookLogStore pattern:

Export a `groupComments` function (pure, testable) and the `useRecipeCommentStore` Zustand store.

`groupComments(comments: RecipeCommentWithProfile[]): ThreadedComment[]`:
- Filter top-level (parent_id === null), sort by created_at ASC
- Group replies by parent_id into a Map
- Return array of `{ comment, replies }` objects
- If a reply references another reply (depth > 1), reparent it to the root comment (client-side enforcement of single-level threading)

Store state interface:
```typescript
interface RecipeCommentState {
  comments: RecipeCommentWithProfile[];
  commentCount: number;
  loading: boolean;
  error: string | null;
  replyingTo: RecipeCommentWithProfile | null;

  fetchComments: (recipeId: string) => Promise<void>;
  addComment: (params: { recipeId: string; userId: string; body: string; parentId?: string | null }) => Promise<boolean>;
  deleteComment: (commentId: string, recipeId: string) => Promise<void>;
  setReplyingTo: (comment: RecipeCommentWithProfile | null) => void;
  clearComments: () => void;
}
```

`fetchComments`: Query `recipe_comments` with `select('*, profiles(handle, avatar_url)')` filtered by `recipe_id`, ordered by `created_at ASC`. Also fetch `comment_count` from `recipes` table (single select on `recipes.comment_count` where id = recipeId).

`addComment`: Optimistically add comment to state array (generate temp UUID with `crypto.randomUUID()`), then insert via supabase. On success, re-fetch all comments for consistency. On failure, remove optimistic entry and set error. Return boolean success.

`deleteComment`: Optimistically remove from state array (and decrement commentCount), then delete via supabase. On failure, re-fetch to restore correct state.

`setReplyingTo`: Set the `replyingTo` state to the provided comment or null.

`clearComments`: Reset comments to [], commentCount to 0, loading false, error null, replyingTo null.

Import `getErrorMessage` from `../lib/errors`. Import types from `../types/database`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> Supabase RLS | User input (comment body) crosses into database |
| client -> RLS SELECT | Comment visibility scoped by household membership + follow relationships |
| client -> RLS DELETE | Delete authorization checks comment ownership or recipe creator status |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-47-01 | Tampering | comment body length | mitigate | DB CHECK constraint `char_length(body) <= 500` enforced server-side regardless of client maxLength |
| T-47-02 | Information Disclosure | recipe_comments SELECT | mitigate | RLS SELECT policy requires household membership OR active follow relationship via kitchen_profiles/follows join |
| T-47-03 | Elevation of Privilege | recipe_comments DELETE | mitigate | RLS DELETE policy: `auth.uid() = user_id OR recipes.created_by = auth.uid()` -- only author or recipe creator |
| T-47-04 | Spoofing | recipe_comments INSERT user_id | mitigate | RLS INSERT WITH CHECK: `auth.uid() = user_id` prevents inserting as another user |
| T-47-05 | Tampering | comment_count | accept | Count maintained by SECURITY DEFINER trigger, not client. Client optimistic values overwritten on refresh |
| T-47-06 | Information Disclosure | comment on private recipe | mitigate | RLS INSERT requires `is_household_member(r.household_id, auth.uid())` via recipes join |
</threat_model>
